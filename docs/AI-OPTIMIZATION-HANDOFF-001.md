## 1. 项目当前真实状态

ResearchWorkbench 是一个个人研究平台，当前目标不是替用户认定“最好的论文”，而是帮助研究生理解候选方向、按路线阅读论文、学习 Agent 技术、查看每日精选并保存本人阅读记录。

当前已存在的主要能力：

- 三个已批准的候选方向：
  - 代码智能体的修复正确性与预算受限验证；
  - 动态多源知识下的可信检索与回答；
  - 部分观测图数据中的有害融合识别。
- 论文按“当前路线重要性 / 读者难度 / 论文类型”三条轴组织，而不是用一个总分替代；
- 区分推荐投入深度与实际交付深度，实际有 `deep / standard / quick / entry` 四种诚实档位；
- 阅读卡已经区分正文精读、正文选读、摘要级和原文入口，并保留来源覆盖、版本、核查日期和限制；
- 有六条 Agent 技术学习主干，强调先修、主资源、自查和何时跳过；
- 有基于 grad-companion 的每日精选工作流，但它是用户调用 harness 后产生的静态内容，不是网页自动调用插件，也不是无人值守定时服务；
- 本人阅读记录与公开 AI 整理内容分离，个人 v3 记录仅在本机保存；
- 当前内容约 45 篇论文卡、3 个方向、11 篇经典、11 条技术路线和 4 期简报；
- 近期已经完成一轮前端设计重构：阅读正文优先、首页有时间锚点、减少徽章与重复免责声明、内容库拆分、保持文本层表达。

因此，当前最重要的问题不是“平台能不能展示内容”，而是：

> **平台是否真的能让一个论文积累很少、尚未形成稳定研究判断力的人，知道下一步为什么读、读什么、读到什么程度，以及读完后能力和问题地图发生了什么变化。**

## 2. 用户当前阶段与真实目标

以下是会话中用户明确提供的背景，不代表平台已经自动验证：

- 已学习过机器学习、深度学习以及 CNN、RNN、Transformer 等基础；
- 本科阶段论文阅读量较少，更多是学习技术和阅读技术文档；
- 对专业大模型方向有较高预期，希望尽早找到适合自己、难度可控、能够持续推进的研究方向；
- 期望未来争取高水平成果，但平台不能承诺 CCF-A 或任何发表结果，也不能把 CCF 期刊和会议混为一谈；
- 目前对强化学习、Agent evaluation、RAG、软件工程研究方法、实验设计、统计检验、LLM post-training 等方面相对薄弱；
- 当前更接近 `research_stage: exploration`，目标是建立方向地图并尽快完成完整的研究循环，而不是马上判断哪篇论文“最有创新”。

这里形成一个关键判断：用户目前没有足够的个人正例/负例来训练“像用户一样筛论文”的个性化模型。若把 personal preference dataset 作为冷启动前提，会形成循环：

```text
需要论文判断力 → 才能提供高质量反馈 → 才能训练个性化筛选
       ↑                                      ↓
       └────────── 但用户正缺少判断力 ──────────┘
```

正确的启动方式不是假装已经有个人品味，而是先借用可解释的专家先验和课程结构，帮助用户逐步形成自己的判断力。

## 3. 总体诊断：四条根因链

### 3.1 论文平台的目标仍偏向“筛掉论文”，而用户现在需要“控制学习曲线”

旧目标容易被表达成：

```text
很多论文 → AI 过滤 → 留下少数值得读的论文
```

这更适合已经有稳定判断函数的研究者。对当前用户，更合理的目标是：

```text
我当前知道什么
    ↓
下一篇最适合建立哪个知识节点
    ↓
读完获得什么概念、方法或问题意识
    ↓
更新知识地图和阅读状态
    ↓
再选择下一篇
```

这不是普通 paper recommender，而是一个带有路线、先修、反馈和下一跳的 adaptive curriculum（自适应学习路径）。

### 3.2 当前路线很有价值，但默认用户已经知道“为什么要沿这条路线走”

现有方向页已经有研究对象、领域现状、选择理由、限制和按阶段的论文路线，这解决了内容真实性和顺序问题。但对新手还缺少三个显式回答：

1. **为什么现在读这篇，而不是只因为它被放在路线里？**
2. **读完后应该能解释什么，或能继续读哪些内容？**
3. **如果暂时看不懂，缺的先修是什么；如果只剩 30 分钟，哪些必须保留？**

如果没有这些信息，路线可能仍然只是“编辑排好的论文列表”，而不是学习脚手架。

### 3.3 当前阅读卡已经有深度和覆盖纪律，但“精简”还没有充分区分 AI 可代劳与本人必须吸收

现有 `deep / standard / quick / entry` 解决的是交付材料有多深，不能完全解决新手阅读时的另一个问题：

> 论文中的哪些内容应该由我亲自看，哪些内容可以让 AI 解释，哪些内容在当前阶段可以跳过？

对于冷启动用户，单纯压缩全文有一个风险：AI 可能把当前看似不重要、实际上是理解后续论文所需的基础内容删掉。

因此需要在现有深度体系上增加“阅读动作分配”，而不是用它替代深度体系：

```text
Preserve：本人必须看，不能只依赖摘要或二次解释
Explain：AI 可以先解释，本人按问题核对
Skip：当前阶段可以跳过，并说明为什么不会破坏主线理解
```

### 3.4 跨 harness 协作的真正问题不是模型角色，而是认知状态如何低损失流动

用户长期使用 Codex、ZCode、WorkBuddy、Cursor 等不同 harness 及多种模型，已经观察到一个问题：让强模型写一篇长文档交给便宜模型，会损失很多局部判断、证据、否定路径和不确定性。

问题可以更准确地表达为：

> **在固定 token 预算、不同模型和不同 harness 之间，怎样表示项目当前所需的认知，使下一位 Agent 不必重新阅读全部聊天，又不会只继承一个过度平滑的结论？**

这使“共享认知状态 + task-specific handoff packet + semantic delta”成为值得研究的方向。但它目前是待验证假设，不是现有平台的直接功能需求。

## 4. 优化方向 A：把产品核心从“论文库”升级为“研究学习脚手架”

### 4.1 建立两个明确模式，而不是强行使用一种 ranking

建议至少区分：

**模式一：探索/冷启动模式**

- 用户还没有稳定的论文判断标准；
- 目标是建立概念地图、形成基本术语和研究问题感；
- 优先考虑认知收益、先修关系、路线覆盖和阅读成本；
- 不把“最新、引用多、性能高、看起来创新”直接当作优先级；
- 允许使用 survey、教材、课程 syllabus、经典论文的 related work 和成熟 reading list 作为专家先验，但要标明依据来源和局限。

**模式二：个人化研究模式**

- 用户已经真实阅读了一批论文，能够给出“很值 / 一般 / 浪费时间”、最有用章节、错误推荐和感兴趣问题；
- 再逐步建立个人 `judgment profile`、反馈记录和小型 eval set；
- 个人反馈可以影响排序，但不能覆盖事实来源、路线必要性和内容覆盖纪律。

这两个模式不能混成一句“根据用户偏好推荐”。当前默认应是探索模式，个人化能力以后从真实阅读中自然长出来。

### 4.2 引入 Learning Leverage，但不要把它做成一个神秘总分

“Learning Leverage”可以作为排序视角：

> 花一段有限时间读完这篇，能让之后多少概念、论文或研究问题变得更容易理解？

它至少可以拆成五个可解释维度：

| 维度 | 需要回答的问题 |
|---|---|
| Foundation | 是否是后续大量工作默认依赖的前置？ |
| Map value | 是否能帮助建立一个领域的坐标系或问题分类？ |
| Research leverage | 是否能帮助理解或提出研究问题？ |
| Entry cost | 以用户当前基础，进入它需要补多少知识？ |
| Actionability | 是否能连接到一个可在短反馈周期内完成的小实验或复现？ |

不要把五项压成一个不可解释分数。可用“高/中/低 + 一句依据 + 不确定性”或排序理由呈现。现有文档已经明确不使用一个总分替代三条论文轴，这条约束应继续保留。

### 4.3 让现有路线变成“节点—前置—下一跳”

每个路线节点建议逐步补充以下语义，而不是立刻扩充大量内容：

- `whyNow`：为什么此时读；
- `learnOutcome`：读完应该能解释什么；
- `unlocks`：会解锁哪些后续论文、技术单元或问题；
- `prerequisites`：真正必要的先修，哪些只是选学；
- `readingActions`：Preserve / Explain / Skip 的建议；
- `uncertainty`：哪些判断只来自摘要、编辑分析或专家先验；
- `nextAction`：读完后的下一步，不等于“继续读下一篇”。

路线仍然要保持少而有序。冷启动首批可以采用“每个知识节点 1 篇地图型材料 + 1–2 篇代表论文 + 1 篇近期工作”的骨架，而不是一开始让用户读 100 篇。

### 4.4 给方向选择增加“研究循环可行性”，但不做发表承诺

用户希望尽早形成成果，这个目标可以被尊重，但不应直接把产品目标写成“找最容易发 CCF-A 的方向”。更可操作的方向比较维度是：

```text
研究问题价值
× 进入成本
× 实验可行性
× 反馈周期
```

尤其要显示反馈周期：

- 是否能用现有模型、公开数据和公开 benchmark 做小规模验证；
- 一个假设从提出到得到反例，是否需要几天、几周还是很长时间；
- 真值、标注、算力、跨仓库泛化等关键成本是否可控。

这不是“容易发表”的判断，而是帮助新手更快完成完整研究循环：

```text
发现问题 → 读相关工作 → 提出假设 → 设计实验
       → 失败/成功 → 解释原因 → 形成下一个问题
```

现有三个方向都可以沿这个视角补充“适合怎样的起步实验、主要阻塞是什么、哪些主张不能仅靠小实验证明”，但不能借此重排已批准方向或宣称方向保证创新。

## 5. 优化方向 B：保留现有阅读卡体系，增加“学习动作层”

### 5.1 不替换现有 deep/standard/quick/entry

现有分级是项目最重要的真实性资产之一，应继续保留：

- `importance` 表示当前路线重要性；
- `difficulty` 表示读者进入成本；
- `type` 决定内容结构；
- `recommendedDepth` 表示建议投入；
- `deliveredDepth` 表示实际材料依据；
- `coverage` 说明实际读到哪里。

新能力只能叠加在其上，不能把 Preserve / Explain / Skip 误当成第五种深度，也不能因为标了“本人必须看”就把摘要级材料冒充正文精读。

### 5.2 卡片首屏应该回答“为什么现在读”

建议在现有 `lead`、`reasons`、`questions` 和路线目的的基础上，形成面向用户的最小首屏：

```text
为什么现在读：填补哪个知识节点
读完应该会：能解释什么，而不是记住多少段文字
它会解锁：后续论文/技术单元/研究问题
当前材料到哪里：摘要、引言、正文哪些部分已核对
现在不需要：哪些内容可以暂时不读
```

这会把“AI 生成了一段总结”变成“用户知道如何使用这段总结”。

### 5.3 Preserve / Explain / Skip 的具体规则

它应该按论文类型配置，不能用一套固定模板：

- **method**：问题定义、输入输出、核心机制、关键对照通常 Preserve；长推导可 Explain；与当前问题无关的扩展实验可 Skip；
- **survey**：分类地图和分支差异 Preserve；单篇工作细节可 Explain；当前路线外的长尾分支可 Skip；
- **evaluation**：测量目标、真值构造、协议、关键发现和外推限制 Preserve；实现细节可按需要 Explain；榜单无关细节可 Skip；
- **system**：需求、架构、数据与控制流、关键取舍 Preserve；常规工程实现可 Explain；不影响当前问题的部署细节可 Skip；
- **theory**：定义、假设、结论、直觉和反例边界 Preserve；证明逐步细节按基础决定；
- **entry**：不得输出内容性判断，只展示身份、原文入口、路线角色和待获取材料。

重要原则：任何 Skip 都要说明“不读它不会破坏哪条理解主线”，否则只是 AI 随意删减。

## 6. 优化方向 C：建立冷启动评价，而不是一开始要求个人正负例

### 6.1 冷启动阶段的监督信号

当前可以使用的不是 personal priors，而是 expert priors：

- 经典教材的章节顺序；
- 高质量 survey 的 taxonomy；
- 课程 syllabus；
- 定义性论文和常用 benchmark；
- 论文 related work 中反复出现的前置工作；
- 成熟研究者的公开阅读路线。

这些信号不能直接证明“必读”，但可以作为临时课程骨架。平台必须标明“依据和不确定性”，不要以引用数或近期程度冒充质量判断。

### 6.2 第一批 eval 评什么

冷启动 eval 不应只问“推荐的论文好不好”，而应问：

- 用户是否理解了为什么读它；
- 读完后是否能够回答卡片自查问题；
- 它是否真的帮助理解了下一篇；
- 是否误删了理解后续所需的基础内容；
- 阅读时间和认知收益是否匹配；
- 用户是否能提出更具体的问题；
- 路线是否出现跳跃、重复或过早进入高门槛论文。

每个 eval case 至少记录：

```text
当前知识状态
推荐论文/单元
推荐理由
必要先修
预期解锁内容
允许的不确定性
理想的下一步
```

一开始可以人工准备少量“路线锚点”作为验收样本，不必马上建设复杂的自动评分系统。

### 6.3 什么时候开始建立个人 judgment profile

当用户真实阅读了约二三十篇、开始能说出哪些内容有价值以后，再收集低负担反馈：

- 很值 / 一般 / 浪费时间；
- 最有用的是哪一部分；
- 哪个地方实际没看懂；
- 推荐的下一篇是否合适；
- 用户自己提出了什么新问题。

此时才逐步生成：

- `judgment-profile`：当前个人判断偏好和研究关注点；
- `feedback`：每次纠正及其理由；
- `eval-set`：固定回归样本；
- `positive/negative examples`：尤其用于审美、写作和界面判断。

这些记录仍然要与“AI 建议”和“本人已读状态”分开，不能因为用户点击或看过网页就自动标记已读。

## 7. 优化方向 D：处理平台前端与内容的 AI 味

### 7.1 当前设计重构已经解决的是“层级问题”，下一步应解决“偏好表达问题”

`DESIGN-REWORK-007` 已经明确修复了：辅助件压过正文、首页缺时间锚点、徽章墙、免责声明重复、装饰性编号等问题。下一步不应再次大规模加组件，而应把审美判断从模糊的“做得高级一点”变成可传递的偏好资产。

### 7.2 建立 design language + preference examples

仅有文字设计规范往往不足以传达“看起来像不像这个产品”。建议以后逐步形成一个小型偏好集：

- 正例：用户认为有阅读感、克制、有记忆点的网页、阅读卡和简报；
- 负例：典型 AI SaaS 三卡片、过度圆角、渐变装饰、无意义 badge、重复 CTA、为了填满而增加 section；
- 对照例：A 比 B 好在哪里；
- 反模式：虽然漂亮但不属于 ResearchWorkbench 的页面；
- 截图或可核查参考；
- 每个例子的“应保留 / 应避免 / 适用范围”。

这比反复说“不要 AI 味”更可执行。对后续 AI 的工作方式应是：

```text
强模型负责提炼视觉与表达判断
普通模型负责按规则修改像素和文案
审查模型只检查是否偏离目标与正负例
```

### 7.3 论文卡文案的反 AI 味原则

不要只用“首先—其次—最后—综上”把所有内容抹平。优先写：

- 这篇论文解决的具体问题是什么；
- 为什么当前路线需要它；
- 哪个机制真正值得用户看；
- 哪些结论只来自摘要或编辑分析；
- 哪些地方可以直接跳过；
- 读完后用户应当能提出什么问题。

“不完整”比虚假的完整更可信。项目现有 coverage、limitations、unknown 和实际交付深度纪律应继续保留。

## 8. 优化方向 E：共享认知状态与 handoff packet

这是两段会话中最值得单独保留的研究方向，但它应与 ResearchWorkbench 产品优化解耦推进。

### 8.1 问题定义

传统跨 harness 协作通常是：

```text
强模型长时间思考
    ↓
写一篇计划/总结文档
    ↓
便宜模型重新解释并执行
```

信息损失主要来自：

- 局部事实被压缩成一句结论；
- 采用某个方案前排除过的路径消失；
- 决策依据和反事实条件消失；
- 置信度和未解决问题被写成确定语气；
- 审美、直觉和隐含偏好无法靠长文档完整传递；
- 下一个 Agent 既可能读太多，也可能漏掉真正相关的少量证据。

共享认知状态的假设是：模型不直接互相传话，而是共同读写一个外部的、可验证的状态；每次工作只产生语义增量；下一个 harness 根据当前任务生成一个有边界的 handoff view。

### 8.2 最小概念模型

不要把“世界状态”理解成一篇巨大的 `context.md`，也不要一开始建设数据库、服务器或多 Agent 编排平台。先用几个概念区分信息：

```text
事实 Facts：代码、文件、测试、来源和可核查观察
目标/约束 Objectives：要做什么、不能做什么、验收标准
决策 Decisions：采用了什么、为什么、排除了什么
假设 Hypotheses：当前相信什么、置信度、如何证伪
任务 Tasks：谁在做什么、状态、依赖和阻塞
证据 Evidence：日志、截图、论文段落、测试结果、diff
偏好 Preferences：审美、表达、产品取舍和正负例
不确定性 Unknowns：尚未确认、可能冲突或需要升级的问题
```

其中事实和证据尽量引用原始位置，决策保留理由和反事实条件，偏好使用例子，不要把四类内容压成同一种 prose。

### 8.3 Handoff packet 不是完整历史，而是当前任务的视图

Shared State 类似项目的长期认知账本；handoff packet 是针对当前任务裁剪出的最小充分上下文。建议最小字段为：

```yaml
task: 当前任务编号或自然语言任务
objective: 本次要完成的结果
current_state: 与任务直接相关的已知状态
constraints: 不可违反的项目契约和范围
relevant_evidence: 原始证据定位，而不是只有总结
decisions: 相关决策、理由、被排除方案、置信度
hypotheses: 仍在验证的假设及失效条件
requested_action: 接收 Agent 应做什么
acceptance: 如何判断完成
unresolved: 不能悄悄假定的问题
escalate_if: 何时停止并请求更强模型或用户
```

示例：

```yaml
task: improve-ranking-eval
objective: 判断当前问题首先是排序目标还是召回不足
current_state:
  - top-30 已包含多数候选，但 top-5 相关性不稳定
constraints:
  - 不改变现有每日发现接口契约
relevant_evidence:
  - E032: eval/ranking-case-17.json
  - E041: logs/search-20260920.jsonl#L143-L177
decisions:
  - id: D017
    claim: 当前优先验证 ranking objective
    confidence: 0.78
    invalidate_if: top-30 实际漏掉大量人工相关论文
hypotheses:
  - id: H011
    claim: embedding recall 是主要瓶颈
    status: downgraded
requested_action: 建立固定样本的排序对照实验
acceptance:
  - 输出 recall@20、nDCG@5 和失败分类
escalate_if:
  - 新证据推翻 D017
```

这里的重点不是字段数量，而是“不只保存最终结论”。下一个 Agent 不需要继承前一个 Agent 的语气，但必须能恢复：当前认为何事成立、依据是什么、什么会推翻它。

### 8.4 Semantic delta：强模型不负责把知识讲完，而负责修改状态

强模型的一次高价值输出可以不是 5000 字计划，而是：

```text
D017 created
H011 downgraded
H014 still unresolved
E053 added
T028 created
```

同时保留每个变更的理由和证据引用。便宜模型只需读取当前相关状态，完成 T028，并在发现失效条件时停止升级。

这不意味着模型不会输出解释；解释应该存在，但不应成为唯一的、不可验证的状态载体。

### 8.5 四类信息的低损失策略

| 信息 | 推荐载体 | 原因 |
|---|---|---|
| 事实 | 原始证据定位、文件/日志/测试/段落引用 | 尽量不重复总结，允许后继 Agent 复核 |
| 决策 | 结论 + 依据 + 被排除方案 + 置信度 + 失效条件 | 保留“为什么这样做”与反事实边界 |
| 目标与约束 | contract、eval、验收标准 | 让结果可验证，而不是靠语气传递 |
| 审美与隐含偏好 | 正负例、对照例、截图、pairwise preference | 纯文字规则难以传递品味 |

### 8.6 Context compiler 是比“共享状态存储”更准确的研究核心

真正困难的部分不是把状态存下来，而是：

```text
长期认知状态
    ↓
按任务、模型、token 预算和权限筛选
    ↓
有边界的 handoff packet
    ↓
Agent 执行
    ↓
输出 semantic patch / evidence
    ↓
验证并合并回状态
```

因此这个方向可以被描述为 `harness-agnostic agent state protocol`，也可以更准确地称为 `agent context compiler`。前者强调共享状态和跨 harness，后者强调“从大量持久状态编译出当前任务的最小充分上下文”。

## 9. 这个通信方向是否真的比写文档更好：必须作为实验假设验证

当前不能直接断言“结构化状态一定比 Markdown 好”。它可能更好，也可能因为 schema 漏掉隐含信息、检索选错内容、维护成本高而更差。

应比较至少四种条件：

1. 仅给仓库/项目当前材料；
2. 给完整原始对话或轨迹；
3. 给自由形式 handoff 文档；
4. 给结构化 state + task-specific packet。

在尽量相同的 token 预算和任务难度下测量：

- 任务成功率；
- 重新发现信息的时间或 token 成本；
- 关键决策是否一致；
- 证据是否能被后继 Agent 找到并复核；
- 错误假设是否被继续传播；
- 遇到歧义时是否正确升级；
- 维护协议本身的额外成本；
- 对代码任务、内容生产、界面审查和研究路线规划是否有不同结果。

可将“重新接手一个被中断任务需要付出的成本”作为重要结果指标，但会话中提到的论文、博客、仓库名称都应在后续真正阅读前自行核查，不能因为曾在聊天里出现就当作已验证来源。

### 9.1 发表可能性

这个方向有研究潜力，因为问题可以被清楚地转化为：

> 在跨模型、跨 harness、固定 token 预算的任务接管中，哪种信息表示能够以更低成本保留后续工作的有效信息？

但“有潜力”不等于“容易发表”或“保证 CCF-A”。需要有：

- 明确的信息表示对照；
- 任务和接管协议；
- 公平的 token/时间/模型预算；
- 可复现的状态与 packet 生成方式；
- 失败模式分析，而不只是平均成功率；
- 说明结构化协议在哪些任务上有效、在哪些任务上损失审美或隐含知识。

首个原型不应与 ResearchWorkbench 首版产品强绑定。最好先用一个极薄、可手工重放的协议验证思想，再决定是否抽成独立项目或论文原型。

## 10. 建议的优先级路线

### P0：先冻结产品解释，不写新平台架构

产出：一页产品定位和用户阶段说明。

明确 ResearchWorkbench 当前首要价值是：

> 帮助论文积累较少的研究生建立研究地图、控制学习曲线、完成第一批有效阅读和研究循环。

同时声明：它不承诺发表，不自动判断本人已读，不把三个方向当成同时开展的三个项目。

### P1：补一条真实可走的冷启动路线

从现有三方向和经典书目中，每个方向先挑少量路线锚点，补齐：

- why now；
- learn outcome；
- prerequisite；
- unlocks；
- Preserve / Explain / Skip；
- 当前覆盖与未知。

优先改内容契约和少量代表卡，不先建设新的推荐后端。

### P2：把 `reading_profile` 从“调节难度”升级为“学习状态输入”

先用显式、可审查的字段表达：

- 已知背景；
- 薄弱背景；
- 当前研究阶段；
- 当前可用时间或阅读目标；
- 正在追踪的知识节点；
- 最近一次阅读后的自查结果。

不要做黑箱画像打分，也不要把用户未填写的信息静默补成事实。

### P3：建立冷启动 eval，再收集低负担反馈

先测试“路线是否能教会东西”，再测试“是否像用户的个人品味”。真实阅读后再收集个人反馈，逐步形成 judgment profile 和 preference examples。

### P4：补充前端与文案偏好资产

建立少量正例、负例、对照例和反模式，服务于论文卡、方向页、简报和后续前端迭代。继续遵守 `DESIGN-REWORK-007` 的“文本优先、不过度增加视觉组件、不借机重排已批准内容”。

### P5：单独做 Agent communication 小实验

先手工维护很小的 state、evidence、decision、task 和 handoff packet；比较自由文档与结构化 packet。只有实验显示协议确实降低接管成本后，再考虑 CLI、schema 校验、snapshot、adapter 或 MCP。

## 11. 不建议现在做的事情

- 不要立刻把平台改成自动化多 Agent 编排器；
- 不要一开始建设数据库、事件总线、服务器或复杂 agent framework；
- 不要为“世界状态”设计一套巨大且不可维护的 schema；
- 不要让强模型先写大量总文档，再让便宜模型盲目执行；
- 不要把个人偏好、AI 建议、来源覆盖和本人阅读状态写进同一个字段；
- 不要因为一个排序误判就不断向 `tiering.md` 添加例外规则；先记录反馈，再判断是否形成稳定模式；
- 不要把当前摘要级卡扩写成看似完整的精读卡；
- 不要用“最容易发 CCF-A”作为方向推荐的承诺；
- 不要为了验证通信协议修改用户个人记录或初始化新的插件数据；
- 不要把聊天中出现的外部论文、仓库、博客名称当作已经核查过的依据。

## 12. 后续 AI 的首个任务包建议

如果要把本文件交给另一个 AI，建议只要求它先做以下工作：

```text
你正在接手 ResearchWorkbench 的方案讨论，而不是直接编码。

请先阅读：
AGENTS.md、docs/SPEC.md、docs/BACKLOG.md、
docs/READING-TEMPLATES-005.md、docs/TECH-LEARNING-005.md、
docs/DAILY-BRIEF-006.md、docs/DESIGN.md、docs/DESIGN-REWORK-007.md、
docs/AI-OPTIMIZATION-HANDOFF-001.md。

你的任务：
1. 复述当前项目事实，区分用户事实、AI 建议和待验证假设；
2. 对 P0–P5 逐项判断依赖、风险和最小可行产出；
3. 先提出一个不改代码的冷启动路线试验；
4. 为该试验设计 3–5 个可人工核查的验收案例；
5. 单独说明哪些内容属于未来的 Shared Cognitive State / Handoff Packet 研究，
   不要把它直接并入首版产品实施。

除非用户另行授权，不修改代码、不修改 private/、.grad/、个人阅读记录，
不提交、不推送、不公开部署。
```

## 13. 最终结论

两段会话汇合后的核心方向不是“给平台再加一个 AI 摘要功能”，而是三层演进：

```text
现有基础：真实来源、分级阅读、方向路线、技术主干、记录隔离
        ↓
近期产品优化：冷启动课程脚手架 + 学习动作分配 + 可验证的下一跳
        ↓
长期研究方向：共享认知状态 + task-specific handoff + context compiler
```

第一层是当前平台必须守住的真实性基础；第二层直接解决用户现在的迷茫和论文冷启动；第三层是值得独立验证的跨 harness Agent communication 研究，不应未经实验就当作产品架构答案。
